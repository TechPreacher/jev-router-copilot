# Plan: Migrating a 200k-LOC Rails monolith to services on Kubernetes

## 1. Problem statement
Monolith slows delivery. Shared deploys, coupled domains and one big DB mean high blast radius, slow CI and teams blocking each other. Goal: separate only domains that gain from independent deploy or scaling, run them on Kubernetes, keep production stable, and keep a rollback path at every step.

LOC does not set service count or timeline. Those depend on domain coupling, DB entanglement, test coverage, team count and ops maturity. Expect a few services plus a smaller core monolith that remains, not a full decomposition.

## 2. Assumptions (no answers supplied, so these stand in)
- Rails 6/7, single relational DB (Postgres or MySQL), Redis, Sidekiq-style background jobs, roughly 60% test coverage.
- Runs today on VMs or PaaS. No Kubernetes in production yet. Cloud provider undecided, so the plan stays provider-neutral.
- 3–5 product teams (about 25–40 engineers). One platform team can be created or staffed.
- Business accepts that feature delivery slows 20–30% during the first 6–9 months.
- No hard compliance deadline. If PCI or HIPAA applies, add 1–2 months for platform controls.

## 3. Success criteria (measured against baseline from Phase 0)
| Metric | Target |
|---|---|
| Deploy frequency, extracted domains | ≥ daily, independent of monolith |
| Lead time for change, median | −50% vs baseline |
| Change failure rate | ≤ baseline, target < 15% |
| MTTR | ≤ 1h for P1 |
| Availability of user-facing SLOs | ≥ 99.9% (or current level, whichever is higher) throughout migration |
| p95 latency on migrated routes | ≤ baseline + 10% |
| Cross-service sync calls per user request | ≤ 3 on critical paths |
| Monolith CI time | −40% |
| Cost | Infra spend ≤ baseline + 25% at steady state |

## 4. Phases
Phases overlap. A gate is passed only on evidence, never on the calendar.

### Phase 0: Discovery and baseline (weeks 0–6)
- Measure DORA metrics, SLOs, p95/p99 latency, error rates and infra cost.
- Map domains with event storming and code analysis: model and table ownership, cross-domain `ActiveRecord` associations, callbacks, shared concerns, and hotspots (churn × complexity).
- Inventory jobs, cron, webhooks, external integrations, auth flows and data-retention rules.
- Score candidate domains on change frequency, scaling need, coupling and team alignment.
- Write ADRs for target architecture, communication style (sync REST/gRPC vs async events) and data ownership.
- **Gate:** baseline dashboards live; domain map signed off; 2–3 ranked extraction candidates; ADRs approved.

### Phase 1: Modular monolith (weeks 4–30, then ongoing)
- Split code into domain packages/engines with explicit public interfaces. Add automated boundary checks to CI (a dependency/privacy checker) and enforce them first on new code.
- Remove cross-domain AR associations and joins. Replace them with interface calls.
- Give each domain its own tables, documented in an ownership matrix. Stop cross-domain writes.
- Add in-process domain events (publish/subscribe) where async coupling will be needed later.
- Raise test coverage on candidate domains. Add contract tests at module interfaces.
- **Gate (per domain):** zero boundary violations; no foreign table writes; coverage on the domain ≥ 80% of critical paths.
- This phase delivers value even if extraction stops. Many domains should stay here.

### Phase 2: Kubernetes readiness, monolith first (weeks 6–24, parallel with Phase 1)
The platform track is kept separate from extraction. First move the monolith unchanged onto Kubernetes.
- **Platform:** managed Kubernetes, IaC, GitOps or pipeline deploys, ingress/gateway, secrets manager, network policies, autoscaling, PodDisruptionBudgets, resource requests and limits, image scanning, a base image standard.
- **Containerize the monolith:** web, job worker and scheduler as separate Deployments. 12-factor config. Logs to stdout. Graceful shutdown handling SIGTERM for in-flight requests and jobs. Readiness and liveness probes.
- **Observability:** structured logs, metrics, distributed tracing (OpenTelemetry-style) with correlation IDs carried across HTTP and jobs, SLO dashboards, alerting runbooks.
- **Migration:** run on Kubernetes in shadow/staging, then shift traffic gradually (5→25→50→100%) behind the load balancer. Keep the old hosts warm for 4 weeks.
- DB stays outside the cluster (managed DB service). Migrations run as a pre-deploy job.
- **Gate:** monolith at 100% on Kubernetes for ≥ 4 weeks; SLOs met; rollback to old hosts rehearsed; on-call trained.

### Phase 3: Strangler extraction, one domain at a time (from about month 6 onward)
Pick the first domain for low coupling and moderate value (e.g. notifications or search, not billing). Steps for each domain:
1. **Facade:** route traffic via gateway/ingress rules or the monolith's internal interface. Flags control the split.
2. **Build the service** behind the existing module interface. Monolith code calls an adapter that can point in-process or remote.
3. **Data ownership** (see §5): copy, sync, verify, then switch writes.
4. **Traffic:** shadow reads, then canary 1→10→50→100%, flag-controlled, with automated rollback on thresholds (§8).
5. **Decommission** the old code path and tables only after the stability window passes.
- **Gate per domain:** 100% traffic for ≥ 4 weeks inside thresholds; data reconciliation diff = 0 (or within agreed tolerance) for 2 weeks; runbooks, dashboards and an on-call owner in place; old code removed.
- Expect 2–4 months per domain early on, dropping to 1–2 months once patterns and templates mature.

### Phase 4: Stabilize and optimize (rolling, after each extraction)
- Cost tuning (right-sizing, autoscaling), SLO review, removal of dead code and tables, ADR updates.
- Decide, with evidence, whether to stop. Leaving the core monolith in place is a valid outcome.

## 5. Data migration and rollback constraints
- **One owner per table.** Other services read through API, events or read replicas/projections. No shared write DB.
- **Pattern:** expand/contract.
  1. Service gets its own schema or DB.
  2. Backfill.
  3. Sync: change-data-capture or dual write through an outbox. Avoid naive app-level dual writes without an outbox.
  4. Shadow-compare reads.
  5. Flip reads.
  6. Flip writes.
  7. Reverse-sync back to the monolith for the rollback window.
  8. Contract: drop old tables.
- **Rollback constraint:** rollback is cheap only while reverse sync runs. After old tables are dropped, rollback means forward-fix. Keep reverse sync for ≥ 4 weeks after the write flip. Destructive schema changes need explicit sign-off.
- **Cross-domain transactions:** replace DB transactions that span domains with sagas or process managers plus compensating actions, using idempotency keys and the outbox pattern. Domains that need strong invariants together stay together.
- **Reporting/BI:** move to a warehouse fed by CDC or events before cross-domain SQL joins break.
- **Migration runtime:** long backfills run as throttled, resumable jobs. Online schema-change tooling for large tables.

## 6. Cross-cutting concerns
- **Background jobs:** split queues by domain first, inside the monolith. Each extracted service owns its workers. All jobs idempotent with retry/backoff and dead-letter queues. Scheduled jobs move to one scheduler per owner (no duplicate cron across replicas; use leader election or a Kubernetes CronJob with `concurrencyPolicy: Forbid`).
- **Auth:** centralize identity (OIDC provider or an auth service extracted early or wrapped). Validate JWTs or token introspection at the gateway; services authorize locally. Service-to-service traffic uses mTLS or workload identity. Session cookie migration needs a dual-accept period.
- **Messaging:** a managed broker (Kafka-, RabbitMQ- or cloud-queue-class). Versioned event schemas in a schema registry or contract repo. At-least-once delivery with idempotent consumers.
- **API contracts:** consumer-driven contract tests in CI. Versioning policy. Timeouts, retries and circuit breakers on every sync call.
- **Observability:** trace IDs across HTTP, events and jobs. Per-service golden-signal dashboards. Each service gets an SLO before it takes production traffic.
- **Dev experience:** service template (repo scaffold, CI, Helm/Kustomize, dashboards, alerts). Local dev with a compose-style setup or remote dev clusters.

## 7. Risks and mitigations
| Risk | Likelihood / impact | Mitigation |
|---|---|---|
| Distributed monolith (chatty sync calls, lockstep deploys) | High / High | Modular monolith first; prefer async events; cap sync hops; contract tests; independent deploy as a gate |
| Data inconsistency during dual-run | Med / High | Outbox + CDC; reconciliation jobs; automated diff alerts; reverse sync |
| Hidden coupling (callbacks, concerns, shared gems) | High / Med | Boundary checker in CI; coupling analysis in Phase 0; extract the least-coupled domain first |
| Platform immaturity causing outages | Med / High | Monolith-on-Kubernetes before extraction; game days; staged traffic; keep old hosts warm |
| Feature-delivery stall / stakeholder fatigue | High / Med | Capacity split (e.g. 70/30 features vs migration); value delivered every quarter; visible metrics |
| Skills gap (Kubernetes, distributed systems) | Med / High | Dedicated platform team; pairing; training budget; external SRE support early |
| Cost growth (clusters, brokers, observability) | Med / Med | Budget guardrails; right-sizing; observability sampling; monthly cost review |
| Latency regressions | Med / Med | p95 budgets per route; caching; co-locate chatty pairs or keep them in the monolith |
| Security gaps (secrets, network, supply chain) | Med / High | Secrets manager; network policies; image scanning and signing; least-privilege RBAC; security review per service |
| Irreversible data step taken too early | Low / High | Contract phase only after a 4-week window and sign-off; backups and PITR tested |
| Endless migration | Med / Med | Explicit stop criteria; periodic go/no-go; accept a remaining core monolith |

## 8. Rollback thresholds (automated where possible)
During canary or ramp, roll back (flag off or traffic back to the monolith) if any of these holds for 10 minutes:
- error rate > baseline + 0.5 pp, or > 1% absolute
- p95 latency > baseline + 20%
- SLO error-budget burn rate > 2× (1-hour window)
- reconciliation diff > 0.01% of records, or any diff on financial or auth data
- queue lag / DLQ growth > 2× normal

A Phase 2 platform cutover rolls back to the old hosts on any P1 incident linked to the platform within the first 2 weeks.

Program-level: pause new extractions if change failure rate > 20%, or if 2+ migration-caused P1s happen in a quarter.

## 9. Staffing
- **Platform/SRE team:** 4–6 engineers, from Phase 0 and permanent.
- **Migration enablement:** 1 architect/tech lead plus 2–3 senior Rails engineers who build the patterns (outbox, adapters, templates).
- **Product teams:** each spends about 20–30% of capacity on its own domain's modularization and extraction. The team that owns a domain extracts it.
- **Support:** DBA/data engineer 0.5–1 FTE during data migrations; security 0.25–0.5 FTE; TPM 1 FTE.
- If staffing is below this, stretch the timeline rather than skip gates.

## 10. Timeline (ranges; overlapping)
| Phase | Range |
|---|---|
| 0 Discovery/baseline | Months 0–1.5 |
| 1 Modular monolith | Months 1–7 for the first domains, ongoing after |
| 2 Kubernetes readiness + monolith on Kubernetes | Months 1.5–6 |
| 3 First extraction (pilot) | Months 6–10 |
| 3 Next 2–4 extractions | Months 9–24, can run in parallel per team |
| 4 Stabilize/optimize | Rolling, after each extraction |

- **Realistic total:** 18–30 months to reach a meaningful set of services plus a slimmer core.
- **Best case** (low coupling, strong tests, experienced team): about 12–15 months.
- **Worst case** (one tangled DB, weak tests): over 36 months, or stop at the modular monolith.

## 11. Governance
- **Architecture review board** (lead architect, platform lead, team leads): approves ADRs and checks each gate. Meets every 2 weeks.
- **Monthly steering:** metrics vs baseline, risk register, budget, go/no-go on the next extraction.
- **Artifacts:** ADR log, domain ownership matrix, risk register, per-service readiness checklist (SLO, runbook, dashboards, on-call, security review, rollback rehearsed).
- **Quarterly stop/continue review:** extract the next domain only if the projected gain (deploy independence, scaling, team autonomy) beats the added operating cost.
